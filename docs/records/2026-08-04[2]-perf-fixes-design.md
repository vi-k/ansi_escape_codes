## Цели и критерии готовности

Берутся все четыре перформанс-находки ревью, в порядке убывания
выигрыша/риска: H3 → M4 → M7 → M5. Каждый фикс — отдельный коммит.
Фикс считается готовым, когда:

1. все существующие тесты зелёные **без правок самих тестов**;
2. `dart analyze --fatal-infos` и `dart format` чистые;
3. числа до/после сняты `benchmark/compare.dart` против пре-фиксного ref
   и приведены в сообщении коммита;
4. класс сложности закреплён ratio-гардом в
   `test/performance_guards_test.dart` (где наблюдаемо);
5. итоговые замеры сведены в подраздел Performance записи 4.0.0
   в CHANGELOG (отдельным заключительным коммитом).

## Шаг 0 — бенчмарк-инфраструктура и утилита сравнения

### Новые сценарии `benchmark/parser_benchmark.dart`

К существующим страницам добавляются:

- **Чистый текст**: большая строка без единого ESC — полный разбор,
  `removeAll`, `ansiHasEscapeCodes` (профиль H3);
- **Нарезка документа**: подготовленный (`prepare()`) парсер, `substring`

- **Память**: большой смешанный вход — число матчей и дельта
  `ProcessInfo.currentRss` после `prepare()` (профиль M5).

Данные фиксированные (генерация с фиксированным сидом), замер — «лучший
из батчей», как в существующих страницах.

### Режим `--json`

Те же замеры, вывод — JSON-строки
`{scenario, metric, value, unit, bytes, dartVersion, mode}` в stdout.
Человекочитаемый режим не меняется.

### `benchmark/compare.dart`

Запуск: `dart run benchmark/compare.dart <baseRef> [headRef]`
(по умолчанию head — текущая рабочая копия).

Механика: `git worktree add` базового ref во временную директорию →
`dart pub get` там → запуск **его собственного**

сценариев; если базовый ref не поддерживает `--json` (например, v3.1.2) —
честное сообщение и завершение без сравнения.

В `.pubignore` добавляется `benchmark/compare.dart`: утилите нужны git и

## Шаг 1 — H3: префильтр `indexOf(ESC)`

Основание: каждая альтернатива `escapeCodesRe` начинается с литерального
`\x1B` (проверено ревью; 8-битный C1 парсер сознательно оставляет
текстом), поэтому префильтр точен. Замеры ревью: чистый текст 10 МБ —
518 мс → единицы мкс с fast-path; цветная страница — ×5; плотная — ×1,8.

### Ядро (`lib/src/parsing/parser/matches/parser_iterator.dart`)

Вместо итерации `escapeCodesRe.allMatches(input, pos)` — цикл:

1. `idx = input.indexOf('\x1B', searchFrom)`; нет ESC → остаток текст,
   конец;
2. `escapeCodesRe.matchAsPrefix(input, idx)`:
   - матч → текст `[pos, idx)` (если непустой) + сущность;
   - null (одинокий/нераспознанный ESC) → ESC остаётся в тексте,
     `searchFrom = idx + 1`, поиск продолжается — ровно как сегодняшний
     `allMatches`, пропускающий несматчившиеся позиции.

### Extensions (`lib/src/extensions/…`)

Ранний выход `if (!contains('\x1B'))` (вернуть `this` / `false` /
`length`) — **только** для функций с ESC-якорными паттернами:
`ansiRemoveEscapeCodes`, семейство `ansiHas*`, `lengthWithoutEscapeCodes`
и остальные по фактическому списку из `patterns.dart`, составляемому на
реализации. Функции по C0-кодам (`ansiRemoveControlCodes` и родня)
fast-path **не получают**.

## Шаг 2 — M4: общий резюмируемый курсор

Основание: `substring`/`_seamAt` сегодня обходят матчи с начала строки на
каждый вызов — O(k·n) при нарезке (замер ревью: 200 строк — 1,89 мс,
800 — 15,45 мс, сходится к квадрату). Кэш `Matches._parsed` уже избавляет
от повторного *парсинга* — устраняется повторный *обход*.

Существующие поля курсора `stateAt` (`_cursor`, `_cursorEnd`,
`_cursorStart`, `_cursorState` в `lib/src/parsing/parser/parser.dart`)
обобщаются в одну приватную структуру «прогулки»: итератор матчей +
плоская позиция + состояние текущего куска. Её используют `stateAt`,
`substring` и `_seamAt` по общему правилу (как сегодня у `stateAt`):
запрошенная позиция не меньше сохранённой → продолжить с места, меньше →
перезапуск с начала. `substring` по завершении оставляет прогулку в
валидном состоянии (на матче, содержащем конец среза), так что нарезка
подряд идёт одним проходом. Семантика всех трёх операций не меняется.

## Шаг 3 — M7: оверхед на плотных входах

Основание: ~50 % времени разбора плотного входа — `namedGroup`-чтения и
аллокации (замеры ревью: 4+ `namedGroup` по ~47 нс на код, конструирование
сущностей ~28 %). Ожидание: суммарно 1,5–2× на плотных входах.

1. **Диспетчеризация типа сущности** по `input.codeUnitAt(idx + 1)`:
   `[` (0x5B) → CSI, `]` (0x5D) → OSC, иначе — ESC-семейство.
   `namedGroup` остаётся только внутри выбранной ветки, где реально нужны
   подгруппы.
2. **`SgrSimpleFunction`** — const-таблица из 108 экземпляров,
   индексируемая `ControlFunctionsSGR.index`, вместо аллокации на каждый
   разобранный простой код (`lib/src/parsing/control_functions/sgr.dart`).
3. **Списки SGR-сущностей** (`lib/src/parsing/parser/entities/sgr.dart`):
   внутренний растущий список + `UnmodifiableListView` (O(1)-обёртка из
   `dart:collection`) вместо `List.unmodifiable` (полная копия) —
   публично по-прежнему неизменяемый список.

## Шаг 4 — M5: память

Основание: полный разбор удерживает ~30× размера входа (замер ревью:
10 МБ входа → +602 МБ RSS): список матчей дублируется, каждый `Text`
держит копию подстроки, плюс кэш плоской строки.

1. **`_MatchesResult`**
   (`lib/src/parsing/parser/matches/matches_result.dart`):
   `UnmodifiableListView` поверх `_parsed` вместо второй полной копии.
2. **`Text`** (`lib/src/parsing/parser/entities/entity.dart`): хранит
   вход + офсеты; `string` — `late final`, материализуется при первом
   доступе один раз (`input.substring(start, end)`). Куски, чьё `string`
   никто не читал, копий не держат; ссылка на вход ничего не добавляет —
   вход и так удерживается `Matches`.
3. **Дартдок `Parser`**: рекомендация итераторного режима для больших
   входов.

**Точка отката**: если (2) заметно замедляет горячие пути (принтер
постоянно читает `entity.string`) или неприемлемо усложняет код —
остаёмся на (1) + (3); это фиксируется замером плотной страницы
бенчмарка до/после шага.

## Эквивалентность (общая для всех шагов)

- Существующие 214 тестов не редактируются и обязаны остаться зелёными.
- Новый инвариант-тест round-trip: конкатенация `entity.string` всех
  матчей побайтно равна входу — на адверсариальном корпусе ревью
  (одинокий ESC в конце, усечённые CSI, OSC без терминатора, суррогатные
  пары, 8-битный C1, `\x00`/`\x7F`, CRLF, 21-значные параметры).
- Существующий дифф-фаззинг extensions-vs-parser расширяется корпусом
  «чистый текст» и «плотные коды».

## Тесты-гарды (`test/performance_guards_test.dart`)

Ratio-подход: ловит смену класса сложности, не константу — устойчив к
шуму CI, идёт в обычном `dart test` на обоих SDK матрицы (3.6.0, stable),
весь файл — секунды.

- **Нарезка (M4)**: подготовленный парсер, срез N строк vs 2N
  (порядка 400/800); лучшее из трёх, отношение времени ≤ 2,5×
  (квадрат дал бы ~4×).
- **Чистый текст (H3)**: разбор + `removeAll` на N vs 2N символов без
  ESC; отношение ≤ 2,5×.
- **Ленивость `Text.string` (M5)**: повторный доступ возвращает
  `identical` объект.
- Честная оговорка: отсутствие второй копии списка в `_MatchesResult`
  снаружи ненаблюдаемо — закрепляется только числами страницы памяти
  бенчмарка.

## Порядок коммитов и рабочий процесс

Ветка `perf/review-findings` от текущего `main`. Перед каждым коммитом:
`dart analyze --fatal-infos`, `dart format`, полный `dart test`.

1. Бенчмарк: новые сценарии + `--json` + `compare.dart` + `.pubignore`.
2. H3 (префильтр) + его гард; числа `compare.dart` в сообщении коммита.
3. M4 (курсор) + гард, с числами.
4. M7 (диспетчеризация/аллокации), с числами.
5. M5 (память) + тест ленивости + дартдок, с числами страницы памяти.
6. CHANGELOG: подраздел Performance в записи 4.0.0 с итоговыми замерами.

В конце — PR, ожидание CI-матрицы, слияние. Версия не бампается: всё
входит в невыпущенную 4.0.0.
