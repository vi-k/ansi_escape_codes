## Проблема

Семантика SGR реализована дважды: парсер
(`lib/src/parsing/parser/entities/sgr.dart`) читает параметры числами и
при нехватке аргументов расширенного цвета потребляет только
интродьюсер+вид; regex-путь (`lib/src/internal/sgr_functions.dart`,
обслуживает шесть поверхностей `ansiHas*`/`ansiRemove*` цветов)
сравнивает текстом и клампит. Отсюда:

- **M2**: `'\x1B[38;2;1;2m'` — парсер видит `fgRgb?;bold;dim`, а
  `ansiRemoveForeground()` съедает всю последовательность вместе с
  bold и dim (клампинг «до конца списка»).
- **M3**: `'\x1B[38;05;196m'` — ведущий ноль ломает текстовое сравнение
  `part == '38'`; удаление цвета оставляет `\x1B[05;196m` — blink+мусор.
  ECMA-48 8.1(f) ведущие нули допускает.
- **Неизвестный вид** (найдено при чтении кода): `'\x1B[38;7;1m'` —
  парсер потребляет `38;7` (unknown-color), regex-путь — только `38`,
  оставляя одинокий `7` (inverse) в выводе.
- **L4**: `sgrPattern` принимает приватные байты `<=>?` в параметрах,
  поэтому `'\x1B[?5m'.ansiHasSgr` — true, а `ansiRemoveSgr` удаляет
  реальные xterm-последовательности (`CSI > 4;1 m` modifyOtherKeys,
  SGR-mouse `CSI < … m`); парсер их корректно классифицирует как
  `CsiPrivate`.

Одно расхождение того же корня заход осознанно оставляет: параметр,
который не читается как число — например, переполняющее `int` число из
23 цифр — для парсера делает всю последовательность `CsiUnknown`, а
regex-путь по-прежнему считает её SGR и цветом
(`'\x1B[38;99999999999999999999999m'.ansiHasForeground` — true). Общее
ядро правил на это не влияет: расхождение живёт в том, чем параметр
вообще признаётся, а не в том, как читается цвет. Известное и принятое
ограничение, за границами этого захода.

## Цели и критерии готовности

Ветка `fix/sgr-classifier` от main. Один фикс — один коммит (red-тест +
фикс + строка CHANGELOG в Fixed невыпущенной 4.0.0 — вместе);
conventional-префиксы; версия не трогается. Порядок коммитов:
**L4 → ядро+M3+M2 → agreement-тесты**.

Фикс считается готовым, когда:

1. существующие тесты зелёные **без правок самих тестов**;
2. `dart analyze --fatal-infos` и `dart format` чистые;
3. red-green соблюдён: падение новых тестов зафиксировано до фикса;
4. поведение парсера не изменилось (он — эталон); это утверждение
   покрыто agreement-тестами.

## Раздел 1 — архитектура

### Общее ядро правил: `lib/src/internal/sgr_rules.dart`

Новый лист-модуль, импортирует только константы `ansi/sgr.dart`
(циклов импортов не создаёт; и парсер, и `sgr_functions.dart` могут его
импортировать):

- `bool isExtendedColorIntroducer(int value)` — 38/48/58
  (`FOREGROUND`/`BACKGROUND`/`UNDERLINE_COLOR`);
- `int extendedColorArgCount(int kind)` — `COLOR_256` → 1,
  `COLOR_RGB` → 3, неизвестный вид → 0;
- dartdoc модуля фиксирует правило потребления одним местом:
  **интродьюсер и вид потребляются вместе; аргументы вида — только
  когда есть все**; нехватка любого — потреблены интродьюсер+вид,
  остальное принадлежит последовательности как обычно. Это правило
  парсера; ядро делает его разделяемым.

Точные сигнатуры — в плане.

### Regex-путь поверх ядра (M2 + M3 + unknown-kind)

`splitSgrFunctions` переписывается: голова каждого параметра
разбирается `int.tryParse` (часть с `:` — colon-форма — числом не
является и остаётся цельной функцией, как сейчас); группировка
расширенного цвета — интродьюсер (по `isExtendedColorIntroducer`) +
вид + `extendedColorArgCount(вид)` аргументов, **если они есть**;
нехватка → группа «интродьюсер+вид». Клампинг до конца списка и
текстовые сравнения уходят. Предикаты `isForegroundFunction` и прочие
уже числовые (`int.tryParse(_head(...))`) — не меняются.

### Сужение `sgrRe` (L4)

`lib/src/parsing/patterns/patterns.dart:18`:
`(?<params>[0-9:;<=>?]*)` → `(?<params>[0-9;:]*)`. Затронуты только
`ansiHasSgr` и `ansiRemoveSgr` (прямые потребители `sgrRe`) и шесть
цветовых поверхностей (через `hasSgrFunction`/`removeSgrFunction`):
приватные CSI на `m` перестают считаться SGR — согласование с парсером.
`csiPattern` и `csiRe` (`ansiHasCsi`/`ansiRemoveCsi`) не меняются:
приватные последовательности — по-прежнему CSI.

### Парсер: adoption без реструктуризации

Поведение парсера не меняется. Он начинает брать счётчик аргументов из
ядра (`extendedColorArgCount`) в `_parseColorFunctionFromParams` — там
lookup заменяет литеральные пары «вид → сколько читать» без ломки
потокового чтения. Если при имплементации замена в каком-то месте
контортит код (например, в colon-ветке `_parseColorFunctionFromValues`,
где счёт связан с локальной адресацией values) — место остаётся как
есть; эквивалентность держит agreement-тест, а не принудительный
общий код. Перф-путь, оптимизированный перф-заходом, не
реструктурируется.

## Раздел 2 — тесты, эквивалентность, порядок коммитов

### Коммит 1 — L4: сужение `sgrRe`

Red-green. Новый файл `test/sgr_private_csi_test.dart`:

- `'\x1B[?5m'.ansiHasSgr` → false; `.ansiHasCsi` → true (не меняется);
- `'\x1B[>4;1m'` и `'\x1B[<35;10;2m'` переживают `ansiRemoveSgr`;
- обычные SGR (`'\x1B[1;38;5;196m'`, colon-формы `'\x1B[4:3m'`,
  пустые параметры `'\x1B[;1m'`, ведущие нули) — по-прежнему матчатся;
- удаление цветов на приватных последовательностях ничего не трогает.

RED: первые пункты падают на текущем паттерне. GREEN: сужение.
CHANGELOG: private-CSI-on-`m` больше не считаются SGR в `ansiHasSgr`/
`ansiRemoveSgr*`.

### Коммит 2 — ядро + M3 + M2 + unknown-kind

Red-green. Новый файл `test/sgr_functions_test.dart` — юнит-корпус
`splitSgrFunctions` и регрессии поверхностей:

- M2: `'\x1B[38;2;1;2mX'.ansiRemoveForeground()` → `'\x1B[1;2mX'`
  (bold и dim выживают);
- M3: `'\x1B[38;05;196mX'.ansiRemoveForeground()` → `'X'`;
  `'\x1B[038;5;196m'` — то же;
- unknown-kind: `'\x1B[38;7;1mX'.ansiRemoveForeground()` →
  `'\x1B[1mX'` (потреблена пара `38;7`, одинокий `7` не остаётся);
- корпус разбиения: `38;5;196` → одна группа; `38;2;1;2;3` → одна;
  `38;2;1;2` → `38;2` + `1` + `2`; `38` в хвосте → `38`; `58;5` →
  `58;5`; colon-формы (`38:5:196`, `38:2::1:2:3`) — цельные; пустые
  параметры; `48;05;…` — числовая голова.

RED: M2/M3/unknown-kind падают на текущем `splitSgrFunctions`.
GREEN: ядро + переписанное разбиение. CHANGELOG: два пользовательских
фикса (усечённый цвет больше не съедает соседей; ведущие нули).

### Коммит 3 — agreement-тесты + adoption в парсере

Новый файл `test/has_agrees_with_parser_test.dart` — зеркало схемы
`remove_agrees_with_parser_test.dart` (тот же генератор, фиксированный
seed): `ansiHasForeground`/`Background`/`UnderlineColor` против ответа
парсера по его функциям; в сиды добавляется направленный
malformed-корпус (усечённые цвета, ведущие нули, unknown-kind,
приватные CSI). Underline-путь включается и в remove-agreement — но
существующий файл не редактируется: направленные underline-кейсы живут
в новом файле. Adoption `extendedColorArgCount` в
`_parseColorFunctionFromParams` — в этом же коммите, под защитой
agreement-тестов; red-green для него нет (эквивалентная
переформулировка).

Существующие тест-файлы не редактируются. Порядок L4 первым: сужение
`sgrRe` меняет вход `splitSgrFunctions` (приватные байты в params
перестают приходить), и корпус коммита 2 пишется уже по суженной
грамматике.

## Процесс

Спека → writing-plans (план с точным кодом, включая сигнатуры ядра) →
subagent-driven-development (свежий имплементер на коммит, ревью после
каждого, финальное whole-branch-ревью) → PR в main. Публикация 4.0.0 —
вне захода, отдельным решением пользователя.
