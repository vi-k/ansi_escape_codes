## Что сломано

ANSI selective reset задаёт терминальное значение свойства, а не отменяет
последнюю операцию над ним. Например, после

```text
foreground red → foreground green → reset foreground
```

терминал показывает свой foreground по умолчанию. `Style` моделирует именно
это состояние. `Stack` сознательно хранит историю и на selective reset снимает
только верхний frame, поэтому в том же примере возвращается к red.

Обе модели полезны, но сейчас они смешаны на обычной поверхности оформления:
`Style.call` реализован через `StackedPrinter`. Поэтому два публичных способа
задать один default style получают разный видимый результат:

```dart
Styles.red('$fgGreen' 'a' '$fgYellow' 'b' '$resetFg' 'c');
Printer(defaultStyle: Styles.red).prepare(
  '$fgGreen' 'a' '$fgYellow' 'b' '$resetFg' 'c',
);
```

В первом результате `c` сейчас green: стек снимает yellow и открывает лежавший
под ним green. Во втором `c` red: обычный парсер возвращает foreground к
терминальному default, а принтер проецирует этот default на внешний red.

Первое поведение не соответствует ни смыслу `SGR 39`, ни обещанию
`Style.call` вернуть внутренний текст к стилю вызывающего. Такая же коллизия
есть у остальных selective reset: `SGR 22`, `23`, `24`, `25`, `27`, `28`,
`29`, `49`, `50`, `54`, `55`, `59`, `65`, `75` и у выбора primary font.

## Принятое решение

Пакет сохраняет две модели, но проводит между ними явную границу.

### Терминальная модель по умолчанию

`Style`, `Parser`, `Printer` и `SinkPrinter` описывают то, что покажет терминал.
Selective reset полностью возвращает соответствующее свойство к терминальному
значению по умолчанию. Если принтеру передан `defaultStyle`, терминальное
значение затем заменяется соответствующим свойством этого style.

`Style.call` относится к этой модели и создаёт обычный
`Printer(defaultStyle: this)`, а не `StackedPrinter`. Разбиение на строки,
перенос ambient style, hyperlink, незавершённой control string и residual SGR
остаются обязанностями того же общего printer pipeline.

Изменение не добавляет новый parser mode, состояние или публичное имя. В коде
выбирается уже существующая терминальная реализация.

### Стековая модель только по явному выбору

`Stack`, `StackedParser`, `StackedPrinter`, `StackedSinkPrinter` и
`runZonedStackedPrinter` остаются публичными и сохраняют нынешнюю семантику:

- setter добавляет уровень истории;
- selective reset снимает один уровень соответствующей истории;
- selective reset пустой истории ничего не делает;
- общий `SGR 0` очищает весь `Stack` до `Stack.terminalColors`.

Эти типы предназначены для иерархически составленного ANSI, где reset
используется как закрытие последней наложенной области. Они не обещают
воспроизводить состояние реального терминала на произвольном ANSI-потоке.
Выбор `Stacked*` означает явный выбор этой интерпретации.

## Вложенные `Styles`

Смена внутреннего принтера не должна ломать основной композиционный сценарий:

```dart
Styles.red('abc${Styles.green('green')}def');
```

Внутренний вызов производит последовательность со смыслом

```text
reset → green → "green" → reset
```

Внешний обычный `Printer` проецирует terminal default на red, поэтому видимые
участки остаются:

| текст | foreground |
|---|---|
| `abc` | red |
| `green` | green |
| `def` | red |

Пробник на живом `main` подтвердил, что текущий `StackedPrinter` и обычный
`Printer` уже дают для этого примера одну каноническую последовательность:

```text
[reset][fg256Red]abc[fg256Green]green[fg256Red]def[reset]
```

Так же сохраняется существующий forgiving-сценарий
`Styles.red('$resetFg' 'hello')`: reset внутреннего текста означает terminal
default, который внешний принтер заменяет на red. Для удержания стиля
вызывающего история предыдущих внутренних setter не нужна.

## Публичный контракт и совместимость

Публичные имена, сигнатуры, entry points и типы не меняются. Семантика
`Stack` и всех явно названных `Stacked*` также не меняется.

Наблюдаемое изменение ограничено `Style.call`: если внутренний сырой ANSI
несколько раз устанавливает одно свойство, а затем делает один selective
reset, текст после reset возвращается к внешнему `Style`, а не к предыдущему
внутреннему значению. Это исправление расхождения с терминалом и обычным
`Printer`, а не новая стековая политика.

Пользователь, которому нужен прежний pop-контракт для иерархически
составленной строки, продолжает явно применять `StackedPrinter` или
`StackedSinkPrinter`.

Версия 4.0.0 не опубликована, поэтому исправление описывается в её текущей
секции `CHANGELOG.md`; версия не повышается.

## Поток данных

`Style.call` по-прежнему:

1. возвращает пустую строку для пустого входа;
2. создаёт один принтер на весь вызов;
3. делит текст по `\n`;
4. передаёт строки по очереди в `prepare`, сохраняя carry между ними;
5. соединяет результаты теми же переводами строк.

Меняется только конкретный тип созданного принтера. `_PrinterBase` получает
`Style` вместо `Stack`, поэтому `Sgr.apply` выполняет терминальные операции
`Style`. Дальнейшая проекция через `changeDefaultsTo(defaultStyle)`, переходы
к видимому состоянию, hyperlink и residual работают существующим общим
кодом.

Новых ошибок и новых fallback-ветвей нет. Неизвестные SGR продолжают идти по
приватному residual-каналу H6.

## Документация

Разница моделей должна быть видна до выбора типа, а не только из примера после
него.

- Dartdoc `Style.call` прямо говорит, что selective reset внутреннего текста
  возвращает свойство к внешнему style через терминальную default-семантику.
- Dartdoc `Stack` сохраняет описание push/pop и добавляет явное
  предупреждение: его состояние после selective reset может отличаться от
  состояния терминала на тех же байтах; общий `SGR 0` остаётся полным reset.
- Dartdoc `StackedParser`, `StackedPrinter`, `StackedSinkPrinter` и
  `runZonedStackedPrinter` называет их иерархической интерпретацией и отсылает
  к обычной паре для терминально точного разбора и печати.
- Разделы `StackedPrinter` и `Parser` в `README.md` сохраняют полезный пример,
  но явно описывают цену: `Stacked*` нельзя использовать для ответа на вопрос
  «что покажет терминал» на произвольном ANSI.
- `README.ru.md` меняется синхронно с английским источником в том же коммите:
  структура, порядок и код примеров остаются одинаковыми.
- `docs/architecture.md` фиксирует границу моделей рядом с описанием пары
  обычных и stacked-принтеров.
- Исправление расхождения `Style.call` и `Printer(defaultStyle: ...)`
  записывается в неизданную секцию 4.0.0 `CHANGELOG.md`.

## Проверки

### Красная регрессия

До изменения реализации тест фиксирует живое исходное расхождение:

```text
внешний default: red
внутри: green → yellow → resetFg
ожидание после resetFg: red
текущее значение после resetFg: green
```

Тест должен быть увиден красным на текущем `main` либо на точной обратной
мутации. Ожидаемые состояния и байты перед написанием плана снимаются
пробником с живого кода; ожидание не подгоняется под реализацию без объяснения
терминальной семантики.

### Обязательные сценарии

1. `Style.call` и `Printer(defaultStyle: тот же style)` дают одинаковые
   видимые состояния для входа с двумя setter одного свойства и selective
   reset.
2. Текст `c` в основном foreground-примере становится red, а не green.
3. `Styles.red('abc${Styles.green('green')}def')` остаётся red/green/red и
   сохраняет снятую пробником каноническую последовательность.
4. Unbalanced reset в `Styles.red('$resetFg' 'hello')` оставляет `hello`
   красным; аналогичный тест сохраняется для атрибута вроде bold.
5. Представители разных reset-семейств подтверждают общий контракт: счётный
   флаг, взаимоисключающий enum, foreground/background и extended color.
6. Существующие тесты `Stack` закрепляют противоположный явный контракт:
   setter → setter → selective reset открывает предыдущий frame, а полный
   reset очищает всё.
7. Отдельный тест на публичных `StackedParser`/`StackedPrinter` делает
   намеренное расхождение с терминалом видимым и не даёт будущей правке
   случайно уничтожить pop-семантику.
8. Многострочный `Style.call`, hyperlink и unknown SGR проходят существующие
   регрессии без изменения наблюдаемого поведения.

Финал проходит все ворота из `AGENTS.md`, включая format, analyze,
`check_entry_points`, generator round-trip, полный `dart test`,
`memory_guard`, dartdoc и publish dry-run. После реализации ветка до merge
проходит CI на SDK 3.6.0 и stable.

## Риски и принятые компромиссы

### Код полагался на неявный pop внутри `Style.call`

Такой код получит терминальный reset вместо прежнего восстановления
внутреннего frame. Это намеренная исправленная семантика: `Style.call`
становится согласован с обычным `Printer`. Для pop остаётся явный
`StackedPrinter`.

### `StackedParser` всё ещё не отвечает состоянием терминала

Это не устраняется: такое различие составляет назначение `Stack`. Риск
снижается явным dartdoc, README и тестом на расхождение, а не попыткой сделать
один тип одновременно двумя несовместимыми моделями.

### Байт-в-байт форма может измениться

Контрактом является видимое состояние и корректное закрытие строки. Там, где
обычный и stacked-принтеры выбирают разные допустимые переходы, точные байты
могут поменяться. Вложенный базовый пример отдельно закрепляется как уже
совпадающий у двух реализаций.

## Отклонённые варианты

### Сделать `Stack` терминально точным

Очистка всей истории свойства на каждом selective reset устранила бы
расхождение, но уничтожила бы назначение `Stack` и существующие публичные
сценарии иерархического закрытия. Владелец выбрал сохранить эту модель.

### Оставить `Style.call` на `StackedPrinter` и только документировать

Так сохранялось бы неожиданное поведение на основной стилевой поверхности:
два равно выглядящих публичных способа продолжали бы красить один текст
по-разному. Документации недостаточно для такого расхождения.

### Автоматически угадывать вложенность входа

В ANSI-байтах selective reset не несёт идентификатора открывающей операции и
не говорит, является ли он концом логической области. Эвристика неизбежно
ошибалась бы на корректном терминальном потоке. Модель выбирается типом API, а
не догадкой парсера.

## Не входит в волну

- изменение reset-семантики `Stack` или удаление `Stacked*`;
- переименование, deprecation или добавление публичного parser mode;
- H8: перенос save-slot `ESC 7`/`ESC 8` между строками принтера;
- изменение residual-канала H6, hyperlink-семантики или unfinished seam;
- новая канонизация известных SGR вне необходимого результата `Style.call`;
- изменение SDK-floor, версии, тег или публикация пакета.
