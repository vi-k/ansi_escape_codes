# Complexity guard, который доказывает измеренную работу

> **Состояние на 2026-08-16:** принята владельцем после brainstorming'а
> 2026-08-16; план и реализация впереди.
> **Что это:** спека переделки `benchmark/complexity_guard.dart` — что
> именно проверяется до таймера, как считается отношение и чем
> доказывается калибровка.
> **Связанные записи:** `2026-08-15[4]-verification-guards-design.md`,
> `2026-08-15[6]-verification-guards-plan.md`,
> `2026-08-16[1]-post-verification-guards-report.md`.

## Зачем

`benchmark/complexity_guard.dart` появился волной verification guards, чтобы
wall-clock отношения не жили в общем `dart test`. Ревью всей ветки нашло в нём
три дефекта, бьющих в его собственный смысл: страж может остаться зелёным, не
измерив почти ничего. Владелец отложил их тогда и взял в работу 2026-08-16.

Всё ниже сверено с кодом на `79104c7`, не с пересказом.

## Что не так сейчас

### 1. Проверка объёма работы тавтологична

`_runScenario` (строка 185) сверяет:

```dart
if (side.logicalRuns != expected.$1 || actualOperations != expected.$2) {
```

Обе половины сравнивают константу саму с собой. `side.logicalRuns` приходит из
`_parseBatch` (строка 52), `expected.$1` — из `_parseBatch` же (строка 60).
`actualOperations` — это то, что вернуло тело: `_timedParse` возвращает `lines`
(строка 253), то есть ровно число, которым его и построили; `_timedSlices` и
`_timedInsertions` возвращают счётчик итераций цикла, ограниченного тем же
`lines`.

Отказ, который это пропускает: тело, делающее меньше работы за итерацию.
`_sink = Parser(page.substring(0, 100)).removeAll()` сохраняет и число
итераций, и присваивание в `_sink`, обе стороны дешевеют пропорционально,
отношение остаётся около единицы — и страж выходит с нулём.

### 2. Якоря проверяют не те тела, которые меряются

Каждый сценарий существует в двух экземплярах. `_anchorSlice` (338) валидирует
`_slices()` (256), а таймер идёт по отдельному `_timedSlices()` (266) — это
разный код с разными циклами. `_anchorInsert` (375) работает на **400**
строках, а измеряется `_insertLines` = **200** (строка 26).

Отказ, который это пропускает: правка измеряемого тела, не задевающая тело
якорное. `maxLength: 1` в `_timedSlices` удешевляет обе стороны, якорь и
счётчик не шелохнутся.

Parse и stack от этого свободны — там якорь и таймер зовут один
`_parsePage`/`_stackPage` и один и тот же API, — но структура позволяет им
разойтись в любой момент.

### 3. Отношение берётся от независимо отсортированных медиан

```dart
firstSamples.sort();
secondSamples.sort();
return (firstSamples[_pairs ~/ 2], secondSamples[_pairs ~/ 2]);
```

(строки 231–233). Чередование пар (221–229) заведено ровно затем, чтобы обе
стороны видели одну и ту же обстановку планировщика. Независимая сортировка это
выбрасывает: медиана первой стороны и медиана второй могут прийти из разных
пар, то есть из разных эпох нагрузки. Всплеск, попавший преимущественно в окна
большой стороны, поднимает только её медиану — и страж краснеет без регрессии в
коде.

### 4. Корпус slice не позиционный

`_slices` и `_timedSlices` строят страницу как `List.filled(lines, _styledLine)`
(257, 267) — все строки одинаковы. Дайджест 400 одинаковых срезов кодирует «эта
строка, 400 раз» и не видит, из какого места страницы читали. В
`test/performance_guards_test.dart` тот же якорь уже сделан позиционным
(коммит `d207423`), и корпуса разошлись.

### 5. Глобальный `_sink` — не проверка сценария

`identical(_sink, _unmeasured)` (131) спрашивает, была ли работа хоть где-то за
процесс. Один живой сценарий отвечает за всех.

## Что решено

Решения владельца, brainstorming 2026-08-16:

- **Wall-clock остаётся.** Вариант с детерминированным счётом операций
  отклонён: он потребовал бы счётчиков внутри `lib/`, то есть правки библиотеки
  ради тестируемости.
- **`lib/` не меняется.** Ни публичный API, ни наблюдаемая семантика.
- **Полосы прежние:** `2.5 / 2.5 / 3.5 / 24.0`. Волна обязана доказать, что они
  держатся на новой статистике. Полоса, переставшая держаться на здоровом
  коде, — находка, а не повод сдвинуть число.

## Устройство

### Одна реализация на сторону

Пары `_anchorX` / `_timedX` / `_slices` исчезают. Сторона сценария описывается
одной записью:

```dart
final class _Side {
  final String label;                     // 'shared parser', '800 lines'
  final int batch;                        // логических прогонов в одном замере
  final Object Function() run;            // единственная реализация; её и меряем
  final String Function(Object) observe;  // считается вне таймера
  final String expected;                  // снято пробником с живого кода
}
```

`run` — то, что исполняет таймер. `observe` превращает результат в строку.
Проверяемое и измеряемое становятся одним кодом физически, а не по договорённости:
разойтись им больше негде.

### Наблюдение вместо счётчика

Проверка объёма работы — сравнение `observe(run())` с `expected`:

- для результатов-строк и списков строк — FNV-1a-32 по произведённым строкам
  плюс их число;
- для stack — структурный ключ: длина разбора и цвета шести последовательных
  `resetForeground`.

`expected` **снимается пробником с живого кода и записывается в план**, а не
выводится рассуждением. Это не константа, которой построен корпус: тело,
померившее усечённую страницу, даст другой дайджест.

Наблюдение снимается **дважды: до серии замеров и после неё**, и оба раза
сверяется с `expected`. Второе ловит тело, которое делает работу на первом
прогоне и вырождается дальше, — мемоизацию, кэш, разделяемое состояние.
Наблюдение и обе сверки лежат вне таймера.

Глобальная проверка `_sink` уходит: её работу делает наблюдение, и делает
по сценарию, а не по процессу.

### Статистика

Чередование пар сохраняется. Меняется то, что из них берут:

- для каждой пары `i` считается своё отношение `ratio_i = second_i / first_i`;
  обе стороны пары измерены рядом, в одной обстановке;
- полосе предъявляется **медиана семи отношений**.

Печатаются: медиана отношений, медианы сторон в мкс/прогон (справочно) и
**крайние отношения пар** — минимальное и максимальное. Последнее делает
шумный прогон видимым: расхождение крайних значений говорит о машине, а
смещение медианы — о коде.

### Корпуса

- **slice** переходит на нумерованные строки, как в
  `test/performance_guards_test.dart`. Номер занимает три цифры (`000`…`799`),
  поэтому обычная ширина строки одинакова на обеих сторонах, 400 и 800, и
  отношение продолжает сравнивать сравнимое.
- **insert**: якорное наблюдение переезжает на те же `_insertLines` = 200,
  которые меряются.
- **parse** и **stack** остаются на своих корпусах.

Все дайджесты после смены корпуса снимаются заново пробником.

### Ошибки и атомарность

- Любой аргумент — `stderr` с `Usage:` и код 64.
- Несовпадение наблюдения до замеров — сценарий не измеряется вовсе, его отказ
  копится и печатается.
- Несовпадение наблюдения после замеров — отказ с указанием, что работа
  выродилась по ходу серии.
- Выход за полосу — отказ с названием сценария, отношением и полосой.
- Отказы **собираются со всех четырёх сценариев**, а не обрывают процесс на
  первом: один прогон должен показывать полную картину. Ненулевой `exitCode`
  ставится в конце.
- Скрипт по-прежнему импортирует только `dart:io` и саму библиотеку, никогда
  `package:test`.

## Что не меняется

- `lib/`, публичный API, пять точек входа, SDK-floor `^3.6.0`, версия.
- Шаг CI: страж уже запускается на stable отдельным шагом, менять его нечем.
- `.pubignore`: страж и так не публикуется.
- Полосы и число пар (`_pairs = 7`).
- `test/performance_guards_test.dart`: его якоря уже позиционны и timer-free.
  Волна выравнивает guard по нему, а не наоборот.

## Чем доказывается

Одно из трёх, что план обязан снять с живого кода, а не вывести:

1. **Здоровые прогоны.** 20 независимых холодных запусков на чистой машине и
   20 под ограниченной нагрузкой (по одному занятому воркеру на физическое ядро
   минус одно, нагрузка поднимается до запуска и снимается после). Все сорок —
   нулевой код возврата. Один прогон стоит ≈4.6 с, вся серия — минуты.
2. **Обратные мутации.** Каждая применяется и снимается по одной; красный
   обязан называть ту полосу или то наблюдение, ради которых мутация внесена:

   | мутация | что должно покраснеть |
   |---|---|
   | `Parser.removeAll` возвращает вход | наблюдение parse |
   | цикл срезов возвращает пустой список | наблюдение slice |
   | `Stack._copyWith` клонирует хвост кадра foreground | отношение stack ≥ 3.5 |
   | `_ParserBase._pieceAt` всегда начинает новый `_Walk` | отношение insert ≤ 24.0 |
   | убрать переигрывание `Pieces._parsed` и перенос `_walk` | отношение insert ≤ 24.0 |
   | измеряемое тело parse берёт `page.substring(0, 100)` | наблюдение parse |

   Последняя строка — новая и проверяет ровно то, ради чего волна затеяна:
   на нынешнем страже эта мутация зелёная.
3. **Здоровый красный не чинится расширением полосы.** Если сорок прогонов не
   выходят чистыми, увеличивается корпус, батч или число пар — после чего вся
   матрица повторяется целиком.

## Чего эта спека не решает

- Полосы под другое железо. Первые прогоны на `ubuntu-latest` (2 vCPU) дали
  2.00 / 2.05 / 2.39 / 41.83 при полосах 2.5 / 2.5 / 3.5 / 24.0 — запас есть,
  но это два прогона, а не распределение.
- Отсутствие no-arg теста в `test/tool/complexity_guard_cli_test.dart`.
  Отклонение согласовано владельцем 2026-08-15: полный прогон стража внутри
  `dart test` вернул бы ту конкуренцию за планировщик, ради устранения которой
  он и вынесен.
- Символические ссылки, ветка non-`ErrorsResult` в свипе точек входа и текст
  протокола проверки пола coverage — находки соседних ворот, к этой волне
  отношения не имеющие.
