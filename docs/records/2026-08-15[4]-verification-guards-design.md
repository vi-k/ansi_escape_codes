# Замыкание verification-ворот перед публикацией

> **Состояние на 2026-08-16:** принята владельцем 2026-08-15, реализована по
> плану `2026-08-15[6]` и влита в `main` мержем `6b2d1cb` при зелёных feature
> CI `31902380497` и main CI `31902669556` на SDK `3.6.0` и `stable`;
> писалась против `main` @ `887a2f5`.
> **Что это:** спека волны verification guards — M6, M7, M8 и кластер
> M13/L12 одной волной, четырьмя независимыми механизмами.
> **Связанные записи:** `2026-08-15[5]-pre-verification-guards-report.md`,
> `2026-08-15[6]-verification-guards-plan.md`,
> `2026-08-16[1]-post-verification-guards-report.md`.

## Цель волны

Закрыть последние четыре направления из актуального handoff одной волной,
не смешивая их в один механизм:

1. M6 — специальный checker должен видеть исчезновение самостоятельного
   публичного имени из entry point, даже если оставшиеся сигнатуры замкнуты.
2. M7 — генератор должен доказывать, что его registry охватывает каждый файл
   с его `BEGIN`/`END`-маркерами, до первой записи в `lib/`.
3. M8 — coverage-floor должен измерять рукописный код, а не определяться
   512 почти непокрытыми генерируемыми геттерами.
4. M13/L12 — временные стражи должны доказывать корректность измеряемой
   работы и не краснеть из-за соседних тестов или некалиброванной SDK-ноги.

Это hardening процесса разработки. Наблюдаемая семантика пакета, публичный
API и содержимое `lib/` не меняются.

## Живой baseline

### Entry points

`tool/check_entry_points.dart` сейчас строит export namespace каждой из пяти
библиотек прямо под `lib/` и доказывает его замкнутость по публичным
сигнатурам. Это правильная, но более узкая гарантия, чем сохранность самой
поверхности.

На `887a2f5` размеры namespace такие:

| entry point | публичных имён |
|---|---:|
| `lib/ansi.dart` | 510 |
| `lib/ansi_escape_codes.dart` | 1037 |
| `lib/extensions.dart` | 8 |
| `lib/style.dart` | 91 |
| `lib/utils.dart` | 2 |

Удаление `export 'src/extensions/has.dart';` из `lib/extensions.dart`
уменьшает его namespace с восьми имён до семи, но checker по-прежнему
печатает `5 entry points, closed` и выходит с нулём. Исчезнувший
`StringHasEscapeCodesExtension` возвращает только core-типы `String` и
`bool`, поэтому оставшиеся сигнатуры не могут привести closure-walk к нему.

Общие `analyze` и тесты entry points ловят эту конкретную мутацию. M6 не про
их отсутствие: специальное ворото само сообщает успех, не имея независимого
оракула на исчезнувшую поверхность.

### Generated zones

`tool/generate.dart` вызывает `_replace()` для восьми путей. `_replace()`
проверяет маркеры только в уже названном файле. Девятый закоммиченный файл с
теми же маркерами не читается, не переписывается и не попадает в последующий
`git diff --exit-code -- lib/`.

На живом дереве рассогласования нет: восемь `BEGIN` и восемь `END` стоят в
тех же восьми файлах, которые перечисляет генератор. Дефект — отсутствие
доказательства полноты при добавлении следующей поверхности.

### Coverage

Свежий прогон всех 884 тестов дал два знаменателя:

| отчёт | строки | покрыто |
|---|---:|---:|
| весь `lib/` | 2997 | 2387, **79.646%** |
| без `**/style_colors.dart` | 2485 | 2385, **95.976%** |

`style_colors.dart` добавляет 512 строк и только две покрытые. Нынешний floor
`75.0%` поэтому позволяет рукописной части заметно просесть до того, как CI
покраснеет. Комментарий workflow с прежними `97.5%` и `76.0%` уже не описывает
живой корпус.

### Complexity guards

`test/performance_guards_test.dart` содержит четыре wall-clock сценария:
линейность plain parse, построчного `substring`, углубляющегося `Stack` и
выигрыш общего parser cache при серийных вставках.

- Первые два выбрасывают результат работы и проверяют только отношение
  независимых минимумов `bestOf(3)`.
- Stack-сценарий уже имеет хороший якорь: длину, конечный цвет и историю pop.
- Insert-сценарий держит наличие двух оптимизаций отношением `fresh/shared`,
  но не проверяет возвращённые строки.
- Файл исполняется внутри параллельного `dart test` на SDK 3.6.0 и stable,
  хотя пороги снимались не на обеих ногах.
- Под параллельной нагрузкой дважды наблюдались единичные красные прогоны,
  которые не повторились в трёх следующих запусках.

`benchmark/memory_guard.dart` показывает нужную границу: отдельный холодный
процесс, stable-only, фиксированный корпус, якорь `_matchCount`, двухсторонняя
полоса и записанная процедура перекалибровки. Complexity guard не объединяется
с ним в один процесс, потому что прогрев и аллокации исказят RSS-измерение.

## Выбранная архитектура

Четыре направления остаются четырьмя специализированными воротами. Общая
волна даёт им единый цикл планирования, ревью и CI, но не создаёт центральный
`tool/verify.dart`: analyzer namespace, файловый generator registry, LCOV и
wall-clock ratios не имеют полезного общего runtime-контракта.

Отвергнуты два общих варианта:

- минимальные числовые пины и ослабление timing thresholds: компактно, но
  равноразмерная подмена API остаётся невидимой, а конкуренция не исчезает;
- единый verification runner: даёт одну команду ценой лишней связности,
  общего формата ошибок и общего lifecycle для несвязанных проверок.

## M6: точный namespace snapshot

### Оракул

Новый `tool/entry_point_names.json` хранит объект из пяти ключей — путей
`lib/*.dart` — и отсортированных массивов всех имён из их export namespace.
Snapshot фиксирует публичную поверхность, а не топологию реэкспортов:
безвредный перенос цепочки export не красит ворота, если доступные клиенту
имена не изменились.

Списки точные, не нижние полы. Проверка ловит:

- исчезнувшее или переименованное имя;
- неожиданное новое имя, пока изменение API не принято и snapshot не
  обновлён сознательно;
- равноразмерную замену одного имени другим;
- новый `lib/*.dart` без snapshot и stale snapshot удалённой точки входа.

Повторы между зонтичным и узкими входами принимаются. Около 1648 строк
машинного JSON — цена точного API-oracle; компактный direct-export manifest
проверял бы устройство исходников и пропустил бы исчезновение имени внутри
всё ещё экспортируемой библиотеки.

### Режимы checker

Обычный запуск остаётся воротом:

```text
dart run tool/check_entry_points.dart
```

Он:

1. обнаруживает все точки входа прямо под `lib/`;
2. сравнивает их множество с ключами snapshot;
3. для каждой сравнивает missing и unexpected names;
4. выполняет прежний signature-closure walk;
5. печатает число entry points и проверенных публичных имён;
6. выходит с нулём только при успехе обеих гарантий.

Явный `--update-snapshot` пересобирает JSON детерминированно: пути и имена
сортированы, формат стабилен. Этот режим не обходит closure-check и не пишет
snapshot, если анализ или замкнутость сломаны. CI никогда не передаёт флаг;
обновление остаётся видимым API-diff в коммите. Любой другой аргумент даёт
usage и exit code 64.

Диагностика mismatch перечисляет entry point, missing/unexpected имя и
expected/actual counts. Удаление `has.dart` обязано назвать
`lib/extensions.dart` и `StringHasEscapeCodesExtension`, а не только разницу
`8 → 7`.

### Доказательства

Тестовый seam отделяет вычисление/сравнение snapshot и код возврата от
процессного `exit()`. Fixture проверяет missing, unexpected и несовпадение
множества entry points. Отдельная точная мутация в изолированном дереве
удаляет export `has.dart` и запускает только checker: до фикса она зелёная,
после — красная. Старая мутация с неэкспортированным
`ControlFunctionsC0` подтверждает, что closure-диагностика не ослабла.

## M7: замкнутый registry генератора

### Registry и preflight

Восемь путей и вычисленные для них зоны собираются в один ordered registry
`path → lines`. До вызова `_replace()` генератор рекурсивно читает Dart-файлы
под `lib/` и находит точные marker-строки с тем же правилом `trim()`, которым
пользуется замена.

Preflight проверяет до первой записи:

- discovered marker paths строго равны ключам registry;
- каждый зарегистрированный файл существует;
- в каждом marker-файле ровно один `BEGIN`, ровно один `END`, и `BEGIN`
  стоит раньше `END`;
- файл с одним маркером, повторным маркером либо чужая девятая зона — ошибка.

Неизвестные и отсутствующие пути печатаются раздельно и сортированно. После
успеха генератор пишет восемь зон и сообщает их число. Два запуска подряд
идемпотентны.

### Доказательства

Интеграционный fixture создаёт временный `lib/` со всеми восемью известными
путями и девятым marker-файлом. Настоящий script запускается с временным cwd.
Ожидание: ненулевой exit, точный путь девятого файла и байт-в-байт неизменные
все девять файлов. Companion-case без девятого файла проходит и сообщает
восемь зон. Прежние missing/unpaired-marker отказы остаются красными.

Тексты маркеров и восемь генерируемых зон не меняются: emitter-id внутри
каждого файла дал бы шумный diff без усиления выбранной гарантии.

## M8: coverage рукописного кода

Coverage step строит два LCOV-файла из одного test run:

- `coverage/lcov.info` — полный `lib/`, сохраняется в artifact для
  диагностики;
- `coverage/lcov.gated.info` — тот же отчёт со штатным
  `--ignore-files=**/style_colors.dart`, используется только floor-check.

Floor поднимается с `75.0%` до **`95.0%`**. Это примерно один процентный
пункт запаса от живых 95.976%, но больше не прячет потерю рукописного покрытия
за константным генерируемым знаменателем. Нулевой знаменатель остаётся
безусловным отказом.

Workflow-комментарий объясняет принцип и конкретное исключение, но не хранит
текущие проценты, которые устаревают при каждом тесте или новой ветке.

M8 — конфигурационная правка без нового runtime-кода. Владелец явно принял
вместо искусственного unit-теста RED/GREEN-протокол над живым LCOV:

1. полный отчёт содержит `style_colors.dart`, gated — нет;
2. обнуление нескольких `DA:` рукописного файла опускает gated-report ниже
   floor и красит команду;
3. изменение только `style_colors.dart` не меняет gated percentage;
4. пустой LCOV красный;
5. временный floor выше живого значения красный, восстановленный `95.0%`
   зелёный.

## M13/L12: semantics отдельно от wall clock

### Детерминированные anchors

`test/performance_guards_test.dart` перестаёт измерять время внутри общего
`dart test`, но сохраняет детерминированные контракты каждого сценария:

- parse-корпус несёт ANSI sentinel; точный очищенный текст и объём работы не
  позволяют `removeAll()` просто вернуть вход;
- slicing проверяет число срезов и фиксированный digest/краевые значения;
  пропущенный цикл или `substring => ''` красны;
- Stack сохраняет нынешние length, final colour и pop-history assertions;
- серия вставок проверяет число результатов и digest/точные крайние строки,
  поэтому пропуск операций не маскируется быстрым временем.

Ожидаемые строки, counts и digest план снимает пробником с живого кода до
первого изменения и объясняет их из контракта. Падающее ожидание не
подгоняется под реализацию.

### Standalone complexity guard

Новый `benchmark/complexity_guard.dart` запускает те же четыре формы работы в
отдельном процессе. Он принимает ноль аргументов; лишний аргумент печатает
usage и даёт exit code 64.

Измерительный harness:

- прогревает каждый сценарий до измерения;
- измеряет small/large попарно, чередуя порядок внутри серии;
- берёт медиану нечётного числа, от пяти до семи, пар, а не два независимых
  минимума;
- выбирает batch, где один sample длится десятки миллисекунд, чтобы
  разрешение часов и краткий scheduler spike не определяли ответ;
- печатает сырые медианы, ratio, допустимую полосу и название сценария;
- до timer либо отдельным детерминированным проходом проверяет semantic
  anchor и число операций.

Точные размеры corpus, число пар и границы ratio не задаются этой спекой.
План обязан снять их на живом `887a2f5`-потомке серией холодных запусков и
пятью обратными мутациями:

1. no-op/return-input в parse;
2. пустой/пропущенный slicing;
3. возврат копируемых списков в `Stack`;
4. удаление walk carry;
5. удаление pieces cache вместе с walk carry.

Каждая мутация должна покрасить свой anchor или performance-band, а здоровый
guard — пройти 20 последовательных запусков без нагрузки и 20 под одинаковой
контролируемой параллельной CPU-нагрузкой без ложного красного. Если
разделяющей полосы нет, порог не расширяется рассуждением: меняется corpus
или число пар, затем замер повторяется.

### Место в воротах

`dart test` больше не исполняет wall-clock assertions и остаётся одинаковым
на SDK 3.6.0 и stable. Новый guard:

```text
dart run benchmark/complexity_guard.dart
```

добавляется в локальные ворота `AGENTS.md` и отдельным stable-only шагом CI.
Он не объединяется с `memory_guard.dart` и не запускается на 3.6.0: пороги
калибруются на stable, как memory band. `.pubignore` исключает новый
machine-calibrated guard по той же причине, по которой исключает memory guard.

## Ошибки и атомарность

Каждое ворото сообщает собственную причину и завершается ненулевым кодом:

- snapshot mismatch не превращается в generic analyzer error;
- generator mismatch не оставляет частично переписанный `lib/`;
- coverage не проходит на пустом отчёте;
- complexity guard не проходит на неисполненной работе или слишком дешёвой
  заглушке.

M6 и M7 сначала собирают все ошибки read-only и только затем разрешают
write-mode (`--update-snapshot` или генерацию). Диагностика сортирована, чтобы
SDK, ОС и порядок обхода файлов не создавали шумный diff.

## Задачи и зависимости

Одна волна состоит из пяти независимо ревьюируемых задач:

1. точный namespace snapshot и сохранение signature closure;
2. registry/preflight generator;
3. полный и gated LCOV с floor 95.0%;
4. deterministic semantic anchors complexity-сценариев;
5. standalone complexity guard и его калибровка.

Первые три технически независимы. Задача 5 следует за задачей 4: они меняют
одну измерительную поверхность, и wall-clock корпус должен наследовать уже
утверждённые anchors. Общие workflow, AGENTS, architecture, CHANGELOG и
handoff правятся после смысловых задач, чтобы параллельные исполнители не
сталкивались в одних строках.

Каждую задачу выполняет свежий сабагент по TDD/RED-GREEN-протоколу и принимает
отдельный spec+quality reviewer. После них другой reviewer читает полный diff
волны.

## Документация

- `AGENTS.md`: новый complexity gate, точная snapshot-гарантия, замыкание
  generator registry и смысл filtered coverage.
- `.github/workflows/dart.yml`: названия/комментарии и stable-only complexity
  step; полный и gated LCOV.
- `docs/architecture.md`: два прежних механизма ворот уточняются snapshot и
  preflight; coverage и performance guard описываются в подходящем разделе.
- `CHANGELOG.md`: verification hardening неизданной 4.0.0.
- `.pubignore`: новый machine-calibrated guard не попадает в архив.
- `docs/handoff.md`: после merge закрывает M6, M7, M8 и M13/L12 и переносит
  старый handoff в `docs/records/`.

README и `README.ru.md` не меняются: пользовательского контракта и примеров
эта волна не касается. `docs/backlog.md` агенты не редактируют.

## Полные критерии приёмки

- Удаление export `has.dart` красит только `check_entry_points.dart` и
  называет исчезнувшее extension; здоровые пять namespaces совпадают со
  snapshot и остаются замкнуты.
- Новая либо удалённая точка входа требует явного snapshot update.
- Девятая marker-зона красит generator до первой записи; здоровое дерево
  сообщает ровно восемь зон и остаётся идемпотентным.
- Полный LCOV сохраняет generated file; gated LCOV его исключает и держит
  95.0% рукописного floor с защитой от нулевого знаменателя.
- В общем тестовом корпусе нет wall-clock assertions, но каждый complexity
  scenario имеет точный semantic anchor.
- Standalone guard зелёный на серии чистых и нагруженных запусков; каждая
  известная обратная мутация красная.
- `memory_guard.dart` остаётся отдельным холодным процессом и в своей
  существующей полосе.
- Все прежние локальные ворота плюс новый complexity guard зелёные; feature
  CI зелёный на SDK 3.6.0 и stable до merge, затем зелёный main CI.
- Публичный API, `lib/`, SDK-floor `^3.6.0`, версия `4.0.0` и содержимое
  генерируемых зон не меняются.

## Вне рамок

- публикация, тег `v4.0.0` и bump версии;
- поднятие SDK-floor или зависимостей analyzer/test;
- отдельный detector синхронности README и компиляция README snippets;
- исправление других Medium/Low находок старого independent review;
- унификация всех ворот в один runner;
- изменение generator marker text или добавление новой generated surface;
- изменение публичного API ради удобства fixture-тестов.
