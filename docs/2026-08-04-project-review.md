# Executive summary

Пакет `ansi_escape_codes` 4.0.0 (перед публикацией) находится в **очень хорошем
состоянии**: `dart analyze --fatal-infos` — 0 замечаний при строжайшем линт-сете,
214 тестов проходят, pana 160/160, publish dry-run без предупреждений, все 60
сниппетов README дают байт-в-байт заявленный вывод, все 8 примеров работают.
Недавний рефакторинг «одевания» цветов (коммиты 7925c0c, 09e085a) **корректен** —
проверен фаззингом на 30 000 пар `transitTo` против независимого интерпретатора;
побайтовая round-trip-фиделити парсера подтверждена на 42 адверсариальных входах.

Критических дефектов не найдено. Главные риски:

1. **Windows**: неверный порядок восстановления `echoMode`/`lineMode` в
   `currentCursorPos` — на Windows вызов, вероятно, всегда падает и оставляет
   консоль в raw-режиме.
2. **Юникод**: позиции всюду в UTF-16 code units; `insertBefore` может разорвать
   суррогатную пару и породить некорректную строку (подтверждено), а README
   обещает «считает то, что видно».
3. **Двойная реализация семантики SGR** (regex-путь `ansiRemove*`/`ansiHas*`
   против парсера) уже дала три подтверждённых расхождения на граничных входах.
4. **Производительность на чистом тексте**: сканирование regex-движком в ~120 раз
   медленнее префильтра `indexOf(ESC)` — главный резерв для типового сценария
   (фильтрация логов).
5. **Технический долг**: таблица 256 цветов вручную синхронизируется по семи
   поверхностям (~5 800 строк) без генератора, и именно эти таблицы почти не
   покрыты тестами (`style_colors.dart` — 0,4 % строк).

# Project overview

Назначение: работа с ANSI escape-кодами — генерация (константы, `Style`/`Styles`),
разбор (`Parser`/`StackedParser` с ленивым инкрементальным разбором и кэшем),
трансформации строк (`removeAll`, `optimize`, `substring`, `insertBefore/After`,
`padLeft/Right`), печать с переносом состояния между строками
(`Printer`/`StackedPrinter`/`SinkPrinter`), утилиты терминала (`currentCursorPos`,
`tabs`).

Слои (по факту импортов): `ansi/` (сырые константы) → `patterns/` (единый источник
regex) → `internal/`, `ready_to_use/` (готовые строки) → `parsing/` (цвета, control
functions, машина состояний `State`/`Style`/`Stack`, парсер с sealed-моделью
сущностей) → `extensions/` (быстрый regex-путь без парсера). Шесть входных точек
(`ansi_escape_codes.dart` — зонтичная, `ansi.dart`, `parsing.dart`, `style.dart`,
`extensions.dart`, `utils.dart`). Поток данных: строка → `Matches` (ленивый разбор,
кэш) → сущности (`Text`/`Sgr`/`Csi*`/`Osc*`/`Esc*`) с состоянием `S` на каждой →
операции поверх. Единственная зависимость — `meta`.

# Critical and high-severity findings

**Critical — не найдено.**

---

**H1. Windows: неверный порядок восстановления режимов терминала — консоль
остаётся в raw-режиме, вызов всегда падает**
- Severity: **High** (только Windows) | Уверенность: **high** в нарушении
  документированного ограничения SDK, **medium** в точном поведении (нет
  Windows-машины) | SUSPECTED (код подтверждён, среда — нет)
- Файл: `lib/src/utils/current_cursor_pos.dart:43-47`
- Проблема: восстановление идёт каскадом `..echoMode = keep ..lineMode = keep`.
  Документация Dart SDK: на Windows `echoMode` можно включить только при уже
  включённом `lineMode`. При обычной интерактивной консоли (`keep* == true`)
  присваивание `echoMode = true` при ещё выключенном `lineMode` бросит исключение,
  каскад прервётся, `lineMode` не восстановится, а внешний `on Object` превратит
  всё в `UnsupportedError`.
- Сценарий: любой вызов `currentCursorPos` в Windows-терминале.
- Последствия: функция неработоспособна на Windows; терминал пользователя остаётся
  без эха и построчного ввода до конца процесса.
- Рекомендация: восстанавливать сначала `lineMode`, затем `echoMode`, каждый в
  своём `try`.

**H2. Позиции — UTF-16 code units: `insertBefore` разрывает суррогатную пару;
`length`/`pad*` противоречат README**
- Severity: **High** | Уверенность: **high** | CONFIRMED
- Файлы: `lib/src/parsing/parser/parser.dart` (вся позиционная арифметика);
  README.md:43-44, 712 («counts what is seen»)
- Проблема: `Parser('𝄞abc').insertBefore(1, 'X')` даёт code units
  `[D834, 'X', DD1E, …]` — «X» вклинивается между половинами суррогатной пары,
  строка перестаёт быть валидным UTF-16. `length` для `𝄞é` возвращает 4 на два
  видимых глифа; `padRight` выравнивает по code units — эмодзи/CJK ломают колонки.
- Сценарий: вставка/выравнивание в строках с эмодзи — обычное дело в современных
  CLI-логах.
- Последствия: некорректные строки на выходе (потенциально ломают
  downstream-обработку), кривое выравнивание, расхождение документации с
  поведением.
- Рекомендация: минимум — явно документировать семантику code units и бросать
  `RangeError` при позиции внутри суррогатной пары в `insertBefore/After`;
  максимум — счёт в рунах. В любом случае — тесты на не-BMP.

**H3. Сканирование текста между кодами regex-движком: 5–125× медленнее префильтра
`indexOf(ESC)`**
- Severity: **High** (производительность, класс «главный резерв») | Уверенность:
  **high** | CONFIRMED (измерено, эквивалентность вывода проверена)
- Файлы: `lib/src/parsing/parser/matches/parser_iterator.dart:103-104`,
  `lib/src/parsing/patterns/patterns.dart:4-6`,
  `lib/src/extensions/remove.dart:23,91`, `lib/src/extensions/has.dart:7`
- Измерено: 10 МБ чистого текста — `escapeCodesRe.hasMatch` 518 мс против
  `contains('\x1b')` 4,25 мс (122×); `ansiRemoveEscapeCodes` 529 мс против ~8 мкс
  с fast-path. Прототип сканера (`indexOf` + `matchAsPrefix`, идентичные
  результаты на трёх корпусах): цветная страница 1,25 → 0,245 мс (5,1×), чистая
  1,06 мс → 8,4 мкс (126×), плотная — 1,8×.
- Сценарий: фильтрация логов, где большинство строк без кодов — самый частый
  реальный вход.
- Рекомендация: в `_ParserIterator._read` искать следующий ESC через `indexOf`,
  затем `matchAsPrefix`; в `ansiRemove*/ansiHas*/lengthWithoutEscapeCodes` —
  ранний выход `if (!contains('\x1B'))`.

# Medium and low-severity findings

**M1. `Parser.substring` с `close: true` оставляет гиперссылку OSC 8 открытой**
- Severity: Medium | Уверенность: high | CONFIRMED
- Файл: `lib/src/parsing/parser/parser.dart:289-360` (ср. `_closeLink` в
  `_insert`, строки 420-430)
- `substring(0, maxLength: 3)` на строке со ссылкой возвращает
  `a\e]8;;http://u\e\li` без закрытия. Всё, что программа напечатает дальше,
  становится кликабельным и ведёт на чужой URL — ровно тот сценарий, от которого
  `_insert` защищается через `_closeLink`. Рекомендация: отслеживать открытую
  ссылку на месте среза и дописывать `linkClose` при `close: true` (и/или
  документировать, как для insert).

**M2. Regex-путь и парсер расходятся на усечённых расширенных цветах:
`ansiRemoveForeground` удаляет чужие атрибуты**
- Severity: Medium (вероятность низкая — нужен malformed-вход) | Уверенность:
  high | CONFIRMED
- Файлы: `lib/src/internal/sgr_functions.dart:19-38` (клампинг длины) против
  `lib/src/parsing/parser/entities/sgr.dart:212-274`
- Для `\x1B[38;2;1;2m` парсер видит `fgRgb?;bold;dim`, а `ansiRemoveForeground()`
  удаляет всю последовательность вместе с bold и dim — нарушение
  документированного «другие функции последовательности сохраняются»
  (`remove.dart:71-74`). Рекомендация: при нехватке аргументов у `38/48/58`
  потреблять только интродьюсер+вид, зеркаля правило парсера.

**M3. Ведущие нули в параметрах SGR ломают `ansiRemove*`: удаление цвета порождает
другой стиль**
- Severity: Medium (вероятность низкая, но порча тихая) | Уверенность: high |
  CONFIRMED
- Файл: `lib/src/internal/sgr_functions.dart:22-27, 87-90` (текстовые сравнения
  `'5'`/`'2'`/`'38'`)

  blink+мусор; парсер тот же вход читает корректно (`Color256` 196). ECMA-48
  8.1(f) явно допускает ведущие нули. Рекомендация: числовое сравнение через
  `int.tryParse`.

**M4. `Parser.substring` перечитывает строку с начала при каждом вызове — O(k·n)

# Architecture review

**Сильные стороны** (подтверждены пробами): sealed-модель сущностей с сохранением
нераспознанного (`CsiUnknown`/`OscUnknown`/`SgrUnknown*` + байт-в-байт round-trip)
— лучшее решение пакета для будущих расширений спецификации; `base class
CsiCommon` с типизированными уточнениями — исчерпывающий `switch` плюс стабильный
catch-all; sealed `State<S>` с чистым разделением «значение» (`Style`) / «история»
(`Stack`); диффовый `transitTo` как изолированное ядро ценности; ленивый
инкрементальный разбор с общим кэшем и резюмируемым курсором, обоснованный
чек-ин-бенчмарком; единый источник regex (`patterns.dart`) + дифференциальный тест
парсер-vs-regex; типовая защита инвариантов (underline принимает только
`ExtendedColor`, реальные `RangeError` вместо assert'ов); честная дисциплина entry
points в README.

**Слабые места:**
- **Семь параллельных рукописных поверхностей 256-цветной таблицы** (~5 800 строк:
  `ansi/colors.dart`, три файла `colors256/`, enum `color_indexes.dart`, статики
  `Color256`, 783 константы `styles.dart`, геттеры `style_colors.dart`) без
  генератора и без цикл-тестов (M8). Через год любое изменение политики нейминга —
  механическая правка семи файлов. Рекомендация: чек-ин генератор
  `tool/generate.dart` с коммитом результатов. Смягчающий фактор: сама таблица
  заморожена стандартом.
- **Реальная двусторонняя зависимость state ↔ parser**: `Style.call()`
  (`style.dart:192`) строит `StackedPrinter` — value-слой зовёт машинерию
  ввода-вывода; исторический баг P0.3 из SPEC.md был именно этой связкой. Слои
  неразделимы (~5 000 строк одним узлом). Исправимо переносом `call` в extension
  на стороне парсера без смены публичного API.
- **Инверсия слоёв**: ядро парсера тянет `ready_to_use/` (нужно ~6 констант) и
  `extensions/`; «лёгкая» точка `parsing.dart` по зависимостям тащит всё. Дёшево
  чинится выносом констант в лист-модуль.
- **Шесть публичных контрактов entry points** с subset/overlap-семантикой, уже
  дрейфующих (L7); честный минимум — тест экспортов на каждую точку.
- **Двойная реализация семантики SGR** (M2/M3/L4 — три подтверждённых расхождения
  одного корня): нужен один разделяемый классификатор, плюс распространение
  agreement-теста с remove на has и underline-путь.
- **Добавление одного SGR-атрибута — правка 10+ файлов**; позиционное кодирование
  номера протокола в `ControlFunctionsSGR` (ordinal + 30 `reserved_XX`) с уже
  дрейфующими комментариями. Смягчение: sealed-дизайн делает это неломающим для
  потребителей; стоит завести чек-лист и тест `values[i].code == i`.
- Формальные циклы импортов из-за dartdoc-ссылок (`ansi/c0.dart` → parsing) —
  осознанная цена `comment_references`; шэдоуинг
  `Color`/`Colors`/`State`/`Stack`/`Text`/`Match` — дважды оплаченное решение, но
  `rgb`/`gray` как top-level дублируют `Color256.rgb`/`gray` почти без пользы.

# Testing review

Покрытие измерено: **75,2 % строк (1687/2243); без `style_colors.dart` — 97,3 %**.
100 % — обе машины состояний, итератор парсера, цвета, extensions; 97–98 % —
парсер, SGR-сущности, принтер.

**Хорошо проверено** (ассерты, не просто исполнение): SGR-семантика с
colon-субпараметрами и битыми формами; ESC 7/8 через паузу инкрементального
разбора; эквивалентность ленивого `stateAt` свежему парсеру; голдены
`optimize`/`substring`/вставок с гиперссылками; раскрутка `Stack` с
несбалансированными reset'ами; протокол `currentCursorPos` (чанки, шум, пять форм
отказа); дифференциальный фаззинг extensions-vs-parser (5 000 кейсов,
фиксированный seed). Флейкам взяться неоткуда: фейковые терминалы, фиксированный
seed, детерминированный таймаут-путь.

**Приоритетные недостающие тесты** (каждый привязан к конкретному риску):
1. Не-BMP позиции в `stateAt`/`substring`/`insertBefore`/`pad*` — порча
   суррогатов уже продемонстрирована (H2).
2. Цикл-сверка 530 геттеров `StyleColors` с формулой — опечатка слота уезжает
   молча (M8).
3. Цикл-сверка 783 констант `Styles` и 3×256 именованных строковых констант —
   класс бага, дважды чиненный в этом релизе.
4. Стресс глубины `StackedParser`/`StackedPrinter` (10 000 несбалансированных
   открытий) — регресс к старому «throw на пустом pop» всплыл бы только в проде.
5. `tabs` со стопами шире `terminalColumns` — поведение на правом крае не
   запинено.

Тавтологичные тесты есть (L11), но ни одно поведение не покрыто *только* ими.

# Performance and reliability

Базовая линия: ~14 МБ/с разбор смешанной страницы, ~10 МБ/с плотной, линейный
рост на всём измеренном вплоть до 10 МБ патологических входов,
бэктрекинг-безопасные regex, все RegExp компилируются один раз, таблицы констант —
нулевая рантайм-стоимость. `StackedParser` дороже `Parser` всего на ~5 %.
Подозрение на «одевание» цветов в hot path не подтвердилось: ~4 нс/чтение,
`transitTo` 27–147 нс — менять не нужно.

Резервы, по убыванию значимости: префильтр `indexOf(ESC)` (H3, до 126× на чистом
тексте); курсор для `substring` (M4, квадрат → линейность); удержание памяти ~30×
входа (M5); накладные расходы на код в плотных входах (M7, ~1,5–2×).

Надёжность: гонок/дедлоков нет (однопоточная модель, `async` только в
`currentCursorPos`, где подписка корректно отменяется; ресурсные утечки не
найдены), но H1 (Windows raw-режим) — реальный reliability-дефект; L6 маскирует
диагностику отказов DSR.

# Maintainability

Код читается отлично: последовательный стиль, необычно качественные
doc-комментарии (включая «почему»), честный CHANGELOG,
`@internal`/`@visibleForTesting` по делу. Долг сосредоточен в трёх местах:
рукописная семикратная таблица цветов (генератор!), двойная SGR-семантика (один
классификатор), стоимость добавления атрибута (чек-лист + тест ординалов).
Мелочи: опечатки во внутренних именах `intencityStack`/`scripStack`
(`stack.dart:31,42` и далее), двойное копирование списков в каждом push/pop
`Stack` (`List.of` + `List.unmodifiable`, `stack.dart:401-447`) — на реальных
глубинах несущественно, устаревшие SPEC.md/TODO.md.

# Positive findings

Сверх перечисленного в Architecture/Testing: рефакторинг «одевания» цветов
**корректен по построению и по фаззингу** — умышленно «неправильно одетый» цвет,
протащенный через const-конструктор, самоисцеляется на всех путях чтения,
`==`/`hashCode` цветов сознательно игнорируют target, асимметрий нет; все 783
константы `Styles` и все таблицы 256 цветов сегодня внутренне согласованы
(проверено механически); диапазоны валидируются реальными исключениями в release;
выпускная гигиена образцовая (все deprecated сняты одним мажором с указанием
замен, `.pubignore` с пояснениями, pana 160/160); README-сниппеты и примеры —
100 % воспроизводимы.
