# Как работать над этим пакетом

Файл для любого агента: Claude Code читает его через `CLAUDE.md`, Codex —
напрямую. Правила отсюда старше привычек инструмента; всё, чего здесь нет,
решается по репозиторию, а не по памяти инструмента.

## С чего начать сессию

1. **`docs/handoff.md`** — состояние пакета **сейчас**: что зелено, что
   открыто, что ждёт решения владельца, какой следующий безопасный шаг.
   Новый заход начинается с него. **Сюда же идут находки и предложения
   агента** — раздел «Найдено волнами».

   Сессия может оборваться в любой момент, поэтому handoff держится
   актуальным постоянно, а не пишется в конце. Существенно продвинулись —
   обновите его первым.

   **Чего в нём не должно быть:** пересказа истории коммитов (её знает
   git), разбора уже законченных эпизодов (это `docs/records/`) и пожеланий
   владельца (это `docs/backlog.md`). Handoff отвечает на «где мы стоим», а
   не на «как мы сюда пришли».
2. **`docs/backlog.md`** — **список владельца**: что он хочет сделать с
   пакетом. **Агенты в него не пишут.** Читать — да, брать пункт в работу
   — да; заводить свои пункты — нет. Нашли что-то по ходу — в `handoff.md`,
   а владелец сам решит, переносить ли это в бэклог.

   За бэклогом следят: если он не пуст, а обязательной работы нет, —
   предложить владельцу взять пункт. Взятый и доведённый до мержа пункт
   **удаляется оттуда** тем же заходом: это единственная правка бэклога,
   которую агент делает сам.
3. **`docs/records/`** — записи прошлых волн: спеки, планы, отчёты, ревью,
   отработавшие handoff'ы. У каждой в шапке сказано, чем работа кончилась и
   чему в её тексте не верить.

`.superpowers/.../progress.md` — только внутренний ledger исполнения
текущего SDD-плана. Он не заменяет `docs/handoff.md`: точка рестарта,
блокеры и актуальный следующий шаг всегда записываются в handoff.

**Код, тесты и git старше любого из этих документов.** Они писались по
итогам сессий и местами устаревают; если документ расходится с
репозиторием — прав репозиторий. Обратное тоже верно: не переписывать
документ под своё впечатление, не проверив по коду.

## Что это за пакет

Dart-пакет для разбора и печати строк с ANSI-escape-кодами. Публичных
входов пять: `lib/ansi_escape_codes.dart`, `lib/ansi.dart`,
`lib/extensions.dart`, `lib/style.dart`, `lib/utils.dart`; исходники — в
`lib/src/`, тесты — в `test/` (68 файлов), бенчмарки — в `benchmark/`,
инструменты — в `tool/`, примеры — в `example/`.

**Как оно устроено внутри — `docs/architecture.md`**: конвейер разбора,
кто чем владеет и семь механизмов, на которых прошлые заходы
спотыкались. Читать до первой правки в `lib/`. Как пакетом пользуются
снаружи — README.

В `architecture.md` идёт только то, что меняется редко: структура, имена,
границы ответственности. Всё, что живёт от захода к заходу — числа ворот,
открытые находки, состояние ветки, — в `docs/handoff.md`.

Версия **4.0.0 не опубликована** (на pub.dev — 3.1.2), поэтому все правки
неизданные: CHANGELOG правится на месте, а не breaking-нотами, версия не
бампается.

## Ворота

Зелёными должны быть все, прежде чем работа называется сделанной:

```bash
dart format --output=none --set-exit-if-changed .
dart analyze --fatal-infos
dart run tool/check_entry_points.dart
dart run tool/generate.dart && git diff --exit-code -- lib/
dart test
dart run benchmark/memory_guard.dart
dart run benchmark/complexity_guard.dart
dart doc --dry-run
dart pub publish --dry-run   # ожидается 0 предупреждений
```

- **Таблицы цветов генерируются.** Зона между маркерами `BEGIN`/`END` в
  `lib/` — вывод `tool/generate.dart`; править её руками нельзя, ворота
  это ловят. Менять надо генератор.
- **`check_entry_points.dart`** проверяет и замкнутость публичных сигнатур,
  и точный JSON-snapshot namespace каждого entry point. Обычный запуск ловит
  missing и unexpected имена, а также изменение самого множества `lib/*.dart`;
  `--update-snapshot` допустим только при принятом API-diff и в CI не идёт.
  До обоих оракулов инструмент рекурсивно читает все `*.dart` под `lib/` и
  падает на любой диагностике анализатора уровня error или warning: у
  библиотеки, которая не анализируется, модель элементов всё равно есть,
  только меньшая, и без этого свипа `--update-snapshot` записал бы усечённый
  namespace как истину. Info он пропускает намеренно — analyzer API отдаёт
  депрекации, которых `dart analyze --fatal-infos` не показывает.
- **`generate.dart`** до первой записи сверяет registry восьми генерируемых
  зон с marker-файлами, найденными рекурсивно в `lib/`. Лишняя, пропущенная,
  повторная или непарная marker-зона красит preflight атомарно.
- **`memory_guard.dart`** держит удержание памяти в полосе, откалиброванной
  на конкретных машинах; актуальные числа — в `docs/handoff.md`.
- **`complexity_guard.dart`** отдельно держит wall-clock complexity: это
  прогретый standalone process с попарными медианами, только для stable SDK.
  Complexity assertions в `test/performance_guards_test.dart` детерминированы
  и timer-free; нулевой аргумент complexity guard проверяется самостоятельным
  запуском, а не test scheduler.
- CI (`.github/workflows/dart.yml`) гоняет то же на SDK `3.6.0` и `stable`,
  а memory и complexity guards — только на stable. Coverage artifact содержит
  весь `lib/`, но floor 95.0% применяется к отдельному report без
  генерируемого `style_colors.dart`.

## Как здесь принято работать

- **Заход по бэклогу:** brainstorming с владельцем → спека в
  `docs/records/` → план там же → реализация по задачам → финальное ревью
  всей ветки → **пуш ветки и ожидание зелёного CI** → `git merge --no-ff`
  в `main` → `git push origin main`. **PR на GitHub не заводятся, пуш
  разрешён** (владелец сказал это 2026-08-12); тег и публикация —
  отдельное решение, см. ниже.
- **Ветку пушить до мержа, а не после.** CI гоняет `feat/**`, `fix/**` и
  `perf/**` наравне с `main` (`.github/workflows/dart.yml`), и это
  единственное место, где проверяется нижняя нога матрицы — SDK `3.6.0`.
  Локально стоит один SDK, поэтому «зелёные ворота» на машине про эту
  ногу не говорят ничего. Слить непроверенную ветку — значит внести
  красное сразу в `main`.
- **Имена записей:** `docs/records/YYYY-MM-DD[N]-<тема>-<жанр>.md`.
  Квадратные скобки — литералы; `[N]` — порядок внутри дня; дата — дня
  написания документа. `<жанр>` — одно слово о том, **что это за бумага**,
  а не о чём она:

  | жанр | что это |
  |---|---|
  | `design` | устройство и API |
  | `plan` | план работ |
  | `report` | отчёт о сделанном: о волне правок, о разборе дефекта, о предмержевом ревью одной работы |
  | `review` | полное ревью проекта: `project-review`, `architecture-review`, `flutter-review`, `bug-hunter`, `performance-review` — состояние всей кодовой базы глазами ревьюера, а не итог одной работы |

  Нужного слова в таблице нет — взять своё, но по тому же принципу: одно
  слово о жанре записи.

  Жанра `handoff` **нет**: отработавшая точка входа по содержанию — отчёт
  о работе, а «handoff» говорит не о жанре, а о происхождении файла. Тому
  место в шапке, в строке «Что это».
- **Шапка записи.** Каждый файл в `docs/records/` открывается ею, и это
  единственное место, которое потом правится: проза записи остаётся как
  написана, поправки идут в шапку.

  ```markdown
  > **Состояние на YYYY-MM-DD:** что с этой работой сейчас — сделано и
  > смержено (коммит), брошено, частично сделано, пересмотрено позже.
  > **Что это:** одна фраза о содержимом.
  > **Связанные записи:** имена других файлов в `docs/records/`.
  ```
- **Волна закончилась** — её handoff уезжает в `docs/records/` записью
  жанра `report`, а `docs/handoff.md` переписывается под новое состояние.
- **Ожидаемые значения в планах снимаются пробником с живого кода**, а не
  выводятся рассуждением: за две волны они дважды оказались неверны даже
  так. Если тест падает — объяснить почему, а не подгонять ожидание под
  код. Это правило стоит писать прямым текстом в каждое задание
  исполнителю.
- **Коммиты:** один фикс — один коммит, conventional-префикс, тело
  повествовательное по-английски (почему, а не что). Версию не бампать.
- **Чужие правки не коммитить со своими.** В рабочем дереве может лежать
  то, чего агент не делал: незакоммиченная правка владельца, файл от
  инструмента, мусор вроде `.DS_Store`. Добавлять в индекс только то, что
  сделано этим заходом — поимённо, а не `git add -A`. Постороннее не
  трогать: ни коммитить, ни удалять, ни «прибираться» — сказать о нём
  владельцу.
- **Языки:** для владельца и агентов — по-русски (`AGENTS.md`, `docs/` и
  всё в `docs/records/`), общение с владельцем тоже. Публичные артефакты —
  по-английски: `README.md`, `CHANGELOG.md`, dartdoc в `lib/`, сообщения
  коммитов и **тексты ошибок**.
- **`README.ru.md` — перевод `README.md` и держится в актуальном
  состоянии.** Английский — источник: правка одного тянет правку другого
  **тем же коммитом**, расхождение считается дефектом. Перевод не
  публикуется (`.pubignore`), структура, порядок разделов и код примеров
  в нём те же — переводятся проза и комментарии внутри примеров.

## Чего не делать без слова владельца

- `dart pub publish` и тег `v4.0.0`. Пакет к публикации готов с
  2026-08-05; владелец сказал «пока не публикуем» и решения не менял.
- Бампать версию в `pubspec.yaml`.
- Force-push и переписывание истории `main`. Обычный `git push origin
  main` разрешён — см. «Заход по бэклогу».
- Заводить пункты в `docs/backlog.md`: это список владельца. Свои находки
  — в `docs/handoff.md`.
- Менять публичный API или наблюдаемую семантику ради удобства
  реализации — такие изменения проходят через спеку и решение владельца.
- Поднимать SDK-floor `^3.6.0`: он держит `analyzer` 7 и короткий стиль
  `dart format`; подъём — отдельный заход, последствия перечислены в
  `pubspec.yaml` и в шапке `tool/generate.dart`.

## Решения, которые не переоткрывают

- **Канал гиперссылки лежит рядом с `State`, а не внутри.** Ссылка не
  стиль: `SGR 0` её не закрывает, она не вкладывается, её байты несут
  терминатор и `id=`. Обоснование — `docs/records/2026-08-07[1]`, раздел
  «Почему не внутри State».
- **Инвариант `substring` — «где придержаны оба, открытие пришло
  первым».** Напрашивающийся «в любой момент придержано не больше одного»
  ложен; причина и коммит замены (`de1b5bf`) — в
  `docs/records/2026-08-08[1]`.
- **По скорости в `substring` копать нечего** — потолок измерен
  2026-08-08, методика и числа в `docs/handoff.md`.
